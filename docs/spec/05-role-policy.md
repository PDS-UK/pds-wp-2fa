# Role-policy lifecycle and effective enrollment deadlines

**Decision ticket:** [#5 — Define role-policy lifecycle and effective enrollment deadlines](https://github.com/PDS-UK/pds-wp-2fa/issues/5)

**Parent:** [#1 — PDS WP 2FA Wayfinder Map](https://github.com/PDS-UK/pds-wp-2fa/issues/1)

**Decision date:** 2026-08-24

**Scope:** single-site WordPress role policies for interactive 2FA enrollment. This document defines policy state and deadline resolution; it does not define the 2FA method providers, session gate, database technology, or admin UI.

## Decision summary

1. A role policy is identified by the current site and the exact WordPress **role key**, never by its display label or capabilities.
2. WordPress role discovery reads the initialized role registry through `wp_roles()->get_names()`. A newly discovered role gets a disabled policy; the plugin never enables a role implicitly because of its name or capabilities.
3. Policy history is retained when a policy is disabled or its WordPress role disappears. Re-enabling the same policy or seeing the same role key again never starts a new grace period.
4. Activation anchors are immutable. The role-policy activation timestamp and each user/policy affected-since timestamp are written once and are not reset by disable/re-enable, deletion/reappearance, label changes, or grace-period edits.
5. A user with multiple active role policies receives the earliest role deadline. The strictest active policy therefore wins.
6. A user-specific extension is an auditable, absolute deadline for the user’s current unenrolled enrollment cycle. It is applied after multi-role resolution and may move the deadline later, never earlier.

These decisions prevent a role toggle, role recreation, or assignment churn from silently granting a fresh enrollment window while still allowing an administrator to make a deliberate, auditable exception.

## Canonical terms

| Term | Definition and storage meaning |
| --- | --- |
| **Role key** | The exact string used by WordPress as the key in the role registry and in a user’s role-capability data, for example `editor` or `custom_reviewer`. It is the policy identity. |
| **Role label** | The current human-facing display name for a role. It is presentation metadata and is not an identity. |
| **Discovered role** | A role key currently present in the site’s initialized WordPress role registry. |
| **Role policy** | PDS WP 2FA configuration for one site + role key: whether the policy is enabled and the grace-period duration, plus lifecycle timestamps and history. |
| **Active policy** | A role policy that is enabled and whose role key is currently discovered. It requires enrollment for affected unenrolled users when global enforcement is on. |
| **Disabled policy** | A known role policy explicitly configured off, or a newly discovered role with no explicit enablement. It contributes no protection or deadline. |
| **Orphaned policy** | A retained policy whose role key is no longer in the WordPress role registry. It contributes no protection or deadline until that exact key reappears. |
| **Policy activation** | The first transition of a role policy into enabled state. Its `activated_at` timestamp is immutable for the policy identity. |
| **User/policy affected-since** | The first server-observed time at which a user held the role while that role’s policy was active, anchored so that a user already holding the role when the policy activates starts at policy activation. It is immutable for that user + role-key identity. |
| **Enrollment cycle** | The period beginning when a user is protected and unenrolled, ending when enrollment succeeds or an administrator explicitly resets enrollment. Extensions are scoped to this cycle. |
| **Role deadline** | The deadline computed for one user and one active role policy from that policy’s immutable affected-since anchor plus the current configured grace duration. |
| **Base deadline** | The earliest role deadline among the user’s active role policies. |
| **Grace extension** | A user-specific, auditable increase to the current cycle’s deadline. It is stored as an absolute `extension_until`, not as a duration that is recalculated later. |
| **Effective enrollment deadline** | The deadline used by enforcement: the base deadline, or the later of the base deadline and the current cycle’s extension deadline. An enrolled user has no applicable enrollment deadline. |

All timestamps are UTC instants generated by the server’s injected clock. Durations are non-negative integer seconds. A deadline is inclusive of no grace at the boundary: enforcement is required when `now >= effective_deadline`.

## WordPress facts that shape the design

WordPress exposes a site’s initialized global `WP_Roles` instance through [`wp_roles()`](https://developer.wordpress.org/reference/functions/wp_roles/). `WP_Roles::get_names()` returns an associative list of role keys and display names, and `WP_Roles::is_role()` checks whether a role key is currently registered. The role registry is site-specific in multisite; this plugin is single-site, so the current site is the policy scope. [WP_Roles reference](https://developer.wordpress.org/reference/classes/wp_roles/), [`get_names()`](https://developer.wordpress.org/reference/classes/wp_roles/get_names/), [`is_role()`](https://developer.wordpress.org/reference/classes/wp_roles/is_role/)

The core role structure keeps the role key separate from the stored display name. `WP_Roles::add_role()` accepts both a role key and a display name, and does nothing when the key already exists. `WP_Roles::remove_role()` removes the key from the role registry, role objects, and display-name map. Therefore, a label change with the same key is not a new PDS policy, while a key change is a different identity. [WordPress `WP_Roles::add_role()` source](https://developer.wordpress.org/reference/classes/wp_roles/add_role/), [WordPress `WP_Roles::remove_role()` source](https://developer.wordpress.org/reference/classes/wp_roles/remove_role/)

When WordPress builds a `WP_User`, [`WP_User::get_role_caps()`](https://developer.wordpress.org/reference/classes/wp_user/get_role_caps/) selects only capability-data keys that are currently registered roles. A removed role can therefore remain in raw user metadata without being a current WordPress role, and it must not count as an active PDS policy until the key is registered again. User role mutation methods update user metadata and expose [`add_user_role`](https://developer.wordpress.org/reference/hooks/add_user_role/), [`remove_user_role`](https://developer.wordpress.org/reference/hooks/remove_user_role/), and [`set_user_role`](https://developer.wordpress.org/reference/hooks/set_user_role/) actions. These actions are useful reconciliation triggers; the policy resolver must still reconcile the current role registry and current `WP_User->roles` before making an enforcement decision.

The [`wp_roles_init`](https://developer.wordpress.org/reference/hooks/wp_roles_init/) action fires after roles are initialized and permits plugins to add roles. Use it to trigger discovery, and perform a final lazy reconciliation before policy resolution so roles added later in the load sequence are included.

## Role discovery and policy state

### Discovery algorithm

At role initialization and immediately before resolving a user:

1. Read `wp_roles()->get_names()` for the current site.
2. For every returned `role_key`, create or update the corresponding PDS role-policy record.
3. Update the current role label snapshot only; never use the label as a lookup key.
4. Mark retained policy records whose keys are absent from the current registry as orphaned.
5. Resolve a user only against the intersection of the user’s current WordPress role keys and currently discovered active policy keys.

Discovery is idempotent. It must not change `activated_at`, a user/policy affected-since timestamp, an extension, or an enrollment cycle merely because reconciliation ran again.

### Policy record

The implementation must be able to represent at least:

```text
site_id
role_key
current_role_label
status: disabled | active | orphaned
enabled_configuration: boolean
grace_period_seconds
activated_at: nullable UTC timestamp
discovered_at: UTC timestamp
last_seen_at: nullable UTC timestamp
created_at / updated_at
```

Lifecycle history and extension grants are append-only records, not a replacement for the current policy row. `enabled_configuration` is retained while a role is orphaned so the same key can return to its prior configured state. An orphaned policy is never effective while the key is absent.

Newly discovered roles are `disabled` with `activated_at = null`. An administrator must explicitly enable them. This is a deliberate fail-safe against a plugin or theme adding a powerful role and unexpectedly requiring an incomplete enrollment flow for its users.

### Enable, disable, and re-enable

- **First enable:** set `enabled_configuration = true`, `status = active`, and set `activated_at = now` exactly once. The grace-period countdown for users already holding the role begins from this timestamp.
- **Disable:** set `enabled_configuration = false`, `status = disabled`, and append a policy-disabled audit event. Stop enforcement immediately. Keep the policy row, activation timestamp, user/policy anchors, enrollment-cycle history, and extension history.
- **Re-enable:** set `enabled_configuration = true`. If `activated_at` already exists, preserve it; do not set it to `now`, create a new grace period, clear extensions, or reset affected-since timestamps. Existing unenrolled users may therefore be immediately overdue when enforcement resumes. A user who first becomes affected after re-enable gets an affected-since timestamp at that later observation.
- **Global enforcement off:** do not block requests, but continue maintaining policy state and timestamps. Turning global enforcement back on does not rebaseline any deadline.

There is no implicit “fresh start” operation. A deliberate administrative reset that changes a user’s enrollment state or creates a new role-policy identity must be a separate, explicit, audited operation; ordinary enable/disable is never such a reset.

## Rename, delete, and re-enable behavior

### Role label rename

If the `role_key` is unchanged and only the WordPress display name changes, update `current_role_label`, append one `role_label_changed` event containing the old and new labels, and preserve all policy state. No user deadline changes solely because a label changed.

The plugin must not infer a rename from a new label. A role key changed from `content_reviewer` to `reviewer` is an old-key deletion plus a new-key discovery. The new key starts disabled with no activation timestamp. There is no automatic aliasing or migration because WordPress supplies no role identity beyond the key and the same key may be reused for an unrelated role.

### Role deletion

When a policy’s key disappears from `wp_roles()->get_names()`:

- retain the policy row and all history;
- set `status = orphaned`, `last_seen_at` to the last observation, and append `role_policy_orphaned`;
- make the policy contribute neither protection nor a deadline;
- do not mutate or delete user role-policy anchors or extensions; and
- do not rewrite WordPress user metadata merely to clean up the missing role.

This matches core’s role-registry behavior: `WP_Roles::remove_role()` removes the registered role, while `WP_User::get_role_caps()` only treats currently registered keys as roles. If the raw user role key remains in user metadata and the same key later returns, WordPress may recognize that assignment again; PDS WP 2FA then applies the retained policy and retained timestamps.

### Same-key reappearance

When an orphaned key reappears, clear the orphaned status and restore `active` if `enabled_configuration` is still true, otherwise restore `disabled`. Append `role_policy_reappeared` with the current label. Preserve `activated_at`, affected-since timestamps, enrollment-cycle state, and extension history.

This treats a role key as the durable identity and makes reappearance safe against grace-period laundering. If an administrator intentionally reuses a deleted key for a different business role and wants a clean lifecycle, they must explicitly retire the old policy identity and create a new key; the plugin must not guess that intent.

## Activation anchors and deadline calculation

### Immutable anchors

The implementation must retain two distinct anchors:

1. `role_policy.activated_at`: the first time the role policy was enabled.
2. `user_role_policy.affected_since`: the first time the user was affected by that role policy.

For a user who already holds the role when the policy first becomes active, set `affected_since = policy.activated_at`. For a user first observed holding the role after activation, set `affected_since = first_observed_at`. Equivalently:

```text
affected_since = max(policy.activated_at, first_observed_at)
```

If the user held the role while the policy was disabled, do not start an affected-since record until the policy is first active; the first active policy anchor is the policy’s existing `activated_at`. If a role is removed and later added again, retain the original user/policy anchor rather than granting a new window.

Neither anchor may be updated by:

- role-label changes;
- policy disable/re-enable;
- role deletion/reappearance;
- grace-period changes;
- adding another role; or
- repeated discovery.

The anchors are security state. Any correction requires an explicit administrative reset with old value, new value, actor, reason, and timestamp in the audit log.

### Role deadline

For an unenrolled user `u` and active role policy `p`:

```text
role_deadline(u, p) = affected_since(u, p) + p.grace_period_seconds
```

`grace_period_seconds = 0` means enrollment is required as soon as the user becomes affected. A grace-period configuration change takes effect at the next resolution using the unchanged anchor: increasing it moves an existing deadline later; decreasing it can move the deadline earlier. The change must never rewrite the anchor and must produce an audit event containing old duration, new duration, and the affected policy key.

### Multiple active roles

Let `P(u)` be all active role policies whose keys are in the user’s current WordPress role set and that require 2FA. Then:

```text
protected(u) = P(u) is not empty
base_deadline(u) = min(role_deadline(u, p) for p in P(u))
```

The minimum is intentional: the strictest active role wins. A less restrictive role cannot delay enforcement for a user who also holds a more restrictive protected role. If `P(u)` is empty, the user is not protected and the effective enrollment deadline is `null`.

Example:

```text
editor policy: 14 days, affected 2026-01-01 → 2026-01-15
reviewer policy:  3 days, affected 2026-01-03 → 2026-01-06
base deadline: 2026-01-06
```

The resolver must return the contributing role keys and their individual deadlines, not only the minimum. This makes enforcement explainable and gives audit/admin views enough information to show why a user is protected.

## User-specific extension semantics

### Grant and storage

An extension belongs to `(site_id, user_id, enrollment_cycle_id)`, not to one role. Each grant is append-only and stores at least:

```text
user_id
enrollment_cycle_id
granted_until: absolute UTC timestamp
granted_at
granted_by: actor user ID or system source
reason
previous_effective_deadline
new_effective_deadline
```

The admin operation is “extend by duration.” At grant time, compute the current effective deadline and set:

```text
granted_until = max(current_effective_deadline, now) + requested_extension_seconds
```

The resolver uses the greatest unexpired grant for the current cycle. A grant cannot shorten a deadline. Repeated grants intentionally build from the currently effective deadline, making each additional exception visible and auditable.

### Effective deadline with an extension

For a protected, unenrolled user in the current enrollment cycle:

```text
effective_deadline(u) = max(base_deadline(u), extension_until(u, current_cycle))
```

An extension is applied after the multi-role minimum. Thus, it is a user-specific support exception rather than a role-policy change. It remains effective if the user gains a stricter role, but only until its absolute timestamp expires.

### Later policy changes and role changes

- A grace-period increase does not rewrite or delete an extension. If the new base deadline is later, it wins; the extension remains history.
- A grace-period decrease, stricter added role, or role-policy re-enable cannot move the effective deadline earlier than an unexpired extension.
- Disabling a policy or losing all protected roles makes the deadline unenforced but does not delete the extension. If the same policy key returns during the same enrollment cycle, the extension is available again.
- Successful enrollment ends the current cycle’s extension applicability. Keep all grants for audit. If the user later becomes unenrolled through an explicit reset, create a new cycle with no inherited extension.
- Extensions are not silently revoked. If a future administrative control needs revocation, it must append an explicit revocation event with actor, reason, and effective time; normal policy edits are not revocations.

An extension is not a substitute for enrollment and does not mark a session as 2FA-satisfied. It only changes the time at which the unenrolled user must be routed to enrollment.

## Concrete invariants

The implementation and tests must enforce these invariants:

1. `site_id + role_key` is the only role-policy identity; labels and capabilities are never identity fields.
2. A discovered role without explicit enablement is disabled.
3. An orphaned policy never contributes to `protected(u)` or any deadline.
4. A policy is effective only when its key is currently discovered and its configured state is enabled.
5. `activated_at` is null only for a policy that has never been enabled; once set, it never changes.
6. `affected_since` is written at most once for a user + role-key identity and is not reset by assignment churn.
7. `protected(u)` is true exactly when the user’s current role keys intersect the current active policy keys.
8. With multiple active policies, `base_deadline` is the minimum contributing role deadline.
9. `effective_deadline` is never earlier than `base_deadline` while an unexpired extension exists.
10. A grant stores an absolute timestamp and cannot shorten the current effective deadline.
11. Policy discovery, label changes, role deletion/reappearance, and policy toggles do not create a fresh enrollment cycle.
12. At `now >= effective_deadline`, an unenrolled protected user is overdue; at `now < effective_deadline`, the grace period remains eligible.
13. A user who is already enrolled does not need an enrollment deadline, but policy resolution still reports the active contributing roles for audit and administration.
14. The resolver is deterministic for the same role registry, user role set, policy records, enrollment state, extension records, and clock instant.
15. Every state-changing administrative operation that can affect a deadline is paired with an audit event containing actor/source, timestamp, role/user scope, old value, and new value.

## Audit implications

The audit stream is append-only and is not the source of truth for current enforcement. It must record at least:

### Role and policy events

- `role_policy_discovered` with role key and initial label;
- `role_policy_enabled`, `role_policy_disabled`, and `role_policy_reenabled`;
- `role_policy_orphaned` and `role_policy_reappeared`;
- `role_label_changed` with old/new labels and the stable role key;
- `role_policy_grace_changed` with old/new duration; and
- explicit anchor or policy-identity resets, if such an administrative operation is added.

Each event includes the original immutable activation timestamp when one exists. A re-enable event must make clear that the timestamp was retained rather than restarted.

### User and deadline events

- `user_role_policy_affected` when an affected-since anchor is first created;
- `user_role_added`, `user_role_removed`, or `user_roles_changed` with before/after role keys where available;
- `enrollment_cycle_started` and `enrollment_cycle_completed`;
- `grace_extension_granted` with requested duration, previous effective deadline, and absolute new deadline;
- `grace_extension_revoked` only for an explicit revocation; and
- `enrollment_deadline_reached` at most once per user/cycle unless a later cycle begins.

The resolver should not emit an audit row on every ordinary page request. It should expose the contributing role keys and deadline calculation to the admin/status layer, while emitting events for lifecycle transitions and exceptional grants. Do not put session tokens, TOTP secrets, recovery codes, WebAuthn private material, or raw challenge data in these events.

WordPress’s role mutation actions provide useful event triggers: `add_user_role` and `remove_user_role` fire after the corresponding user change, while `set_user_role` supplies the new role and old roles. The implementation must pair these triggers with reconciliation because the security decision is based on the current WordPress registry and current user role set, not on an event being observed successfully. [Role mutation references](https://developer.wordpress.org/reference/classes/wp_user/set_role/)

## Acceptance checklist

- [ ] Role policies are keyed by site + exact WordPress role key, with labels stored only as mutable display metadata.
- [ ] Discovery uses the initialized WordPress role registry; new roles are disabled until explicitly enabled.
- [ ] Disable, delete, re-enable, label rename, and same-key reappearance behavior matches this document, including retained timestamps and history.
- [ ] First policy activation and first user/policy affected-since timestamps are immutable and tested against repeated reconciliation.
- [ ] A user with multiple active roles is protected by the earliest contributing role deadline, and the resolver exposes all contributors.
- [ ] Grace-period edits use unchanged anchors and are audited; they do not create a fresh grace period.
- [ ] Extensions are absolute, user/cycle-scoped, append-only grants applied after the multi-role minimum, and never shorten a deadline.
- [ ] Enrollment completion ends extension applicability for that cycle without deleting audit history.
- [ ] Missing roles and stale raw role keys do not protect a user until WordPress registers the key again.
- [ ] Lifecycle, role-change, deadline, and extension audit events include actor/source, timestamps, scope, and old/new values without secrets.
- [ ] Boundary tests enforce immediately at `now == deadline`, preserve an extension across policy edits, and prevent role toggles from laundering grace.
